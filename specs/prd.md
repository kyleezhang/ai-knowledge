# AI 学习助手 PRD

## 1. 产品概述

### 1.1 产品名称
AI 学习助手

### 1.2 产品定位
AI 学习助手是一个面向 AI 技术学习的知识管理系统。它一方面会自动采集高价值 AI 技术动态，另一方面也支持用户主动提供资料；系统会先对资料进行处理和理解，再通过 Agent 与用户展开深入交流，在达成共识后先生成结构化 `Note JSON`，再导出为高质量 Markdown 笔记，沉淀为可持续复用的长期知识库。对象字段、目录落盘与 schema 契约统一以 `specs/schema.md` 为准。

### 1.3 核心价值
产品的核心价值不只是“收集”或“总结”，而是建立一条完整的知识闭环：

- 自动发现高价值 AI 技术信息
- 支持用户主动导入重点学习资料
- 通过对话帮助用户真正理解材料
- 将讨论结果沉淀为高质量 Markdown 知识资产
- 在后续问答中优先基于已沉淀笔记进行回答

## 2. 背景与问题

AI 技术信息呈现出高频更新、来源分散、噪声大、理解成本高的特点。高价值内容分布在论文、代码仓库、技术社区、公众号文章、视频、文档和个人资料中，学习过程往往存在以下问题：

- 信息很多，但缺少统一入口和持续筛选
- 总结很多，但未必真正符合用户的理解与关注点
- 笔记很多，但没有形成可复用的知识系统

用户需要的不是一个简单的 RAG 问答工具，也不是一个被动的笔记仓库，而是一个能参与学习过程的 AI 助手：它能够先理解材料，再和用户讨论，最后在共识基础上产出正式知识笔记。

## 3. 产品目标

### 3.1 总体目标

- 建立 AI 技术资料的统一采集与导入入口
- 支持多模态资料的处理、理解与讨论
- 在讨论基础上生成正式 Markdown 笔记
- 让沉淀下来的笔记成为后续问答与思考的主要知识来源

### 3.2 成功标准

- 系统能够同时支持自动采集资料与用户主动导入资料
- 每份重点资料都能形成“理解 -> 讨论 -> 确认 -> 笔记”的闭环
- 生成的 Markdown 笔记具备统一结构和可追溯来源
- 系统能够基于已沉淀笔记回答后续问题

## 4. 非目标

第一阶段产品不追求以下目标：

- 替代完整的学术研究管理工具
- 无需用户参与即可自动形成完全可信的知识结论
- 覆盖 AI 之外的广泛知识领域
- 一开始就支持所有平台的双向同步
- 对所有外部内容源提供完美、稳定、无门槛接入

## 5. 目标用户

### 5.1 主要用户
持续关注 AI 工程、研究、工具和产品动态的技术型个人学习者。

### 5.2 用户特征

- 会主动追踪 AI 相关技术变化
- 会阅读论文、博客、代码、文档、视频和社区讨论
- 希望把零散输入变成结构化知识资产
- 希望 AI 参与“理解和讨论”，而不是只做“总结和检索”

## 6. 信息来源

系统支持两大类信息来源。

### 6.1 自动采集来源

- GitHub Trending
- Hacker News

这部分来源用于持续发现值得关注的 AI 技术动态与高价值材料。自动采集内容不会直接进入主学习流程，而是先进入候选池，形成轻量 `Candidate`，经去重、过滤、评分和推荐后，再由用户选择是否转为正式 `Source`。

### 6.2 用户主动提供来源

- 飞书文档
- Markdown 文件
- PDF 文件

这部分来源代表用户主动指定、希望深入学习和沉淀的材料。用户主动导入的资料会直接创建 `Source`，不经过候选池。

## 7. 核心产品原则

### 7.1 先讨论，后落笔
系统不应将每份资料直接生成最终笔记，而应先给出理解、暴露不确定性、提出问题，并通过与用户的讨论逐步收敛。

### 7.2 笔记代表已确认知识
正式生成的知识笔记应代表用户确认过的理解，而不是模型单次输出的结果。MVP 中，`Note JSON` 是主真相，Markdown 是导出视图。

### 7.3 所有结论都应可追溯
每一份笔记都应保留来源信息、原始链接、关键证据或相关上下文，便于回溯。

### 7.4 知识会持续复利
每一份新生成的笔记都应进入知识库，并在未来问答、关联分析和主题学习中继续发挥作用。

## 8. 核心使用场景

### 8.1 被动发现
系统自动从 GitHub Trending、Hacker News、公众号和 arXiv 中采集潜在高价值 AI 技术内容，对其进行筛选和处理。用户从候选内容中选择感兴趣的主题，与 Agent 深入讨论后，生成正式 Markdown 笔记。

### 8.2 主动学习
用户主动上传 PDF、Markdown、飞书文档、视频或图片资料。系统对内容进行解析，给出初步理解和待确认问题，然后与用户多轮交流，在达成共识后生成 Markdown 笔记。

### 8.3 后续追问
用户在未来某个时点提出问题，例如“最近我们对于 AI Coding Agent 的主要结论是什么？”或“我们之前关于长期记忆系统有哪些判断？”系统优先基于已生成笔记进行检索与回答，并在必要时回查原始资料。

## 9. 端到端流程

产品的核心流程如下：

1. 自动采集内容进入候选池，或用户主动导入资料进入系统
2. `Candidate` 经筛选后转 `Source`，或用户导入直接创建 `Source`
3. 系统处理并抽取可理解内容
4. Agent 自动生成 `draft_understanding`
5. Agent 主动与用户展开讨论，并持续更新 `discussion_summary`
6. 用户确认结构化结论
7. 系统生成 `Note JSON`，并导出 Markdown 笔记
8. 笔记通过 QA 后进入知识库并建立索引
9. 后续问答优先检索已确认笔记

### 9.1 资料进入系统
资料可以来自自动采集，也可以来自用户主动上传或导入。自动采集资料先形成 `Candidate`；用户主动导入资料直接创建 `Source`。

### 9.2 候选筛选与 Source 创建
自动采集候选项会先进行去重、过滤和评分；达到阈值后进入推荐列表，由用户选择是否转为 `Source`。用户主动导入资料不经过该环节。

### 9.3 内容处理
系统需针对不同类型资料生成统一的可理解表示，并显式保留原始快照与处理中间产物：

- GitHub Trending / Hacker News：标题、摘要、链接、作者、时间、标签
- PDF：正文提取、章节结构、元数据
- 飞书文档 / Markdown：结构化文本抽取

### 9.4 初步理解
系统基于处理结果自动产出内嵌于 `Source` 的 `draft_understanding`，内容包括：

- 主要观点
- 技术价值与意义
- 新概念与关键术语
- 可疑点、冲突点或模糊点
- 值得和用户进一步讨论的问题

### 9.5 用户讨论
Agent 不只是复述内容，而是要和用户共同完成理解。讨论绑定单个 `Source`，并持续维护结构化 `discussion_summary`。常见互动方式包括：

- 提出澄清性问题
- 质疑尚不稳固的结论
- 将当前材料与既有笔记进行对比
- 讨论对实践、研究或产品的潜在影响

### 9.6 用户确认
只有当讨论收敛且用户明确确认当前结构化结论可以落笔时，系统才会进入正式笔记生成流程。用户确认的是结论，不是 Markdown 草稿。

### 9.7 Note 生成与 Markdown 成稿
系统基于最终对齐后的结论先生成 `Note JSON`，再导出高质量 Markdown。成稿过程允许补全表达，但不得新增未确认结论。

### 9.8 入库与索引
系统将通过 QA 的笔记保存并建立索引，使其可在后续检索、问答和关联分析中被使用。只有 `approved` 状态的 `Note` 进入主知识检索层。

### 9.9 后续问答
系统回答问题时应优先基于已确认笔记；当笔记信息不足时，才将讨论摘要或原始资料作为补充证据来源，并明确标注其未确认属性。

## 10. 功能需求

### 10.1 信息采集与导入

- 系统应支持定期采集 GitHub Trending 和 Hacker News 中的候选 AI 技术内容
- 系统应支持用户导入飞书文档、Markdown 和 PDF
- 系统应为自动采集内容先创建 `Candidate`，保存基础元信息、评分结果与推荐状态
- 系统应为每份 `Source` 保存基础元信息，包括接入方式、内容类型、标题、链接、导入时间、处理状态等

### 10.2 内容处理

- 系统应能对不同资料类型进行文本抽取和结构化处理
- 系统应将不同资料统一转换为内部标准表示，便于后续理解与检索
- 系统应尽量保留原始导入文件或抓取快照，并保存处理中间产物索引
- 系统应将 `draft_understanding` 与 `discussion_summary` 作为 `Source` 内嵌结构维护

### 10.3 理解与讨论

- 系统应为每份 `Source` 自动生成初步理解草稿
- 系统应展示关键信息、潜在问题、不确定点和建议讨论方向
- 系统应支持围绕单个 `Source` 进行多轮对话，并保留原始消息与结构化摘要
- 系统应在讨论时适度参考已有笔记与历史知识
- 系统应基于固定收敛条件判断是否进入可确认状态

### 10.4 笔记生成

- 系统应在用户确认后先生成 `Note JSON`，再导出 Markdown 笔记
- 系统应在笔记中保留来源信息、确认上下文和必要引用
- 系统应支持统一的笔记模板
- 系统应支持笔记状态管理，例如 `draft`、`approved`、`archived`、`superseded`
- 系统应支持版本笔记，但仅在核心结论变化时创建新版本
- 系统应在 Markdown 成稿后执行规则型 QA / lint

### 10.5 知识检索与问答

- 系统应支持基于 `approved` 状态的 `Note` 进行主检索
- 系统应在回答问题时优先引用已沉淀知识
- 系统应采用关键词 / 元数据过滤与向量召回结合的混合检索方式
- 系统应在答案中先给出综合结论，再给出相关笔记或来源指向
- 系统应在必要时补充未确认讨论或原始资料，并明确标注其未确认属性

## 11. Markdown 笔记结构

正式生成的 Markdown 笔记应采用统一模板。第一版建议包含以下部分；其对应主真相字段存放于 `Note JSON` 中：

- 标题
- 日期
- 来源概览
- 为什么值得关注
- 核心概念
- 讨论后的结论
- 我当前的理解
- 未解决问题
- 相关笔记
- 来源链接

建议文件命名规范：

`YYYY-MM-DD-topic-slug.md`

## 12. 知识对象模型

本节描述产品级对象分层；字段级定义、状态枚举、目录落盘和最小校验约束统一以 `specs/schema.md` 为准。

为支持长期演进，系统应明确区分以下对象：

- `Candidate`
  自动采集链路中的轻量候选对象，用于候选池、评分、推荐与转 `Source`
- `Source`
  进入学习流程的正式资料对象，来自用户主动导入或由 `Candidate` 转换而来
- `Draft Understanding`
  系统基于处理结果生成的待讨论理解草稿，作为 `Source` 的内嵌结构存在
- `Discussion Summary`
  围绕单个 `Source` 讨论后的结构化摘要，作为 `Source` 的内嵌结构存在；原始消息单独保存
- `Note`
  最终确认后的知识对象，`Note JSON` 为主真相，Markdown 为导出视图
- `Index Entry`
  用于支持检索与问答的索引对象，MVP 中仅主索引 `approved` 状态的 `Note`

这种分层是产品从“文档问答”成长为“长期知识系统”的关键前提。

## 13. MVP 范围

MVP 目标是验证最关键的产品闭环，而不是一次性覆盖所有能力。

### 13.1 MVP 包含

- 自动采集 GitHub Trending 和 Hacker News 的部分 AI 技术内容
- 自动采集内容先进入候选池，再由用户选择是否转为 `Source`
- 用户导入 Markdown、PDF 和飞书文档
- Agent 自动生成初步理解并主动与用户讨论
- 用户确认后先生成 `Note JSON`，再导出正式 Markdown 笔记
- Markdown 成稿后执行规则型 QA / lint
- 基于已生成且 `approved` 的笔记进行后续问答

### 13.2 MVP 暂不包含

- Notion 与 Obsidian 的完整双向同步
- 多用户协作
- 高级推荐与个性化排序
- 自动发布到外部平台
- 微信公众号接入
- arXiv 深链路处理
- 视频处理链路
- 图片资料处理

## 14. 风险与约束

### 14.1 外部来源接入风险
飞书文档等来源可能存在访问权限、正文抽取边界和格式损耗问题，因此第一阶段应限制在可稳定获取正文的路径内。

### 14.2 理解偏差风险
模型即使能够正确总结内容，也可能无法准确把握用户真正关心的视角，因此“讨论后再落笔”是核心机制而不是可选项。

### 14.3 知识漂移风险
如果系统在后续问答中直接依赖原始资料而忽略已确认笔记，就会逐渐偏离用户真正认可过的知识体系。

### 14.4 成稿失真风险
如果 Markdown 成稿步骤擅自补充推断或改写确认结论，就会破坏 `Note JSON` 作为主真相的边界，因此需要独立成稿约束与 QA 机制。

### 14.5 成本与延迟风险
预处理、多轮讨论、Markdown 成稿与索引更新都可能带来较高的成本和响应延迟，需要在架构上进行分层和异步化设计。

## 15. 待确认问题

- 是否需要把完整对象 schema 进一步固化为独立 spec
- `quality_checks` 的规则集合与失败恢复策略如何定义
- `Index Entry` 的向量引用结构与更新策略如何落地
- 飞书文档的正文抽取边界与格式保真策略如何进一步细化
- 相关笔记关系由人工确认、规则生成还是模型建议主导
- 新版本 `Note` 的触发提示与交互细节如何设计

## 16. 后续演进方向

- 将生成的 Markdown 笔记写回 Notion 或 Obsidian
- 建立主题图谱和笔记关系网络
- 自动生成 AI 学习周报或专题回顾
- 根据用户历史讨论与笔记偏好优化内容筛选
- 支持跨多个来源生成更高层的主题综合笔记
- 扩展更多输入模态，如视频、图片、更多外部来源

## 17. 总结

AI 学习助手是一个围绕 AI 技术学习场景构建的知识系统。它将自动采集与主动导入结合起来，对多模态资料进行处理与理解，通过 Agent 与用户进行深入讨论，并在达成共识后产出结构化 Markdown 笔记，最终形成一个会持续积累、可复用、可追溯的长期知识库。

这个产品最关键的特征不是“能总结”，而是“能把原始信息转化为经过讨论确认的知识”。
