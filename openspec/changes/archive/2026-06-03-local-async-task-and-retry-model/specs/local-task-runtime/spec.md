## ADDED Requirements

### Requirement: Local Task Is Persisted Work Metadata
The system SHALL represent asynchronous local work as a persisted `LocalTask` JSON object. A task MUST include `task_id`, `type`, `status`, `payload`, `retry_policy`, `attempts`, `created_at`, and `updated_at`.

#### Scenario: Task is created
- **WHEN** a workflow enqueues local asynchronous work
- **THEN** the system persists a `LocalTask` JSON object
- **AND** the object includes validated task metadata and payload

#### Scenario: Task payload contains raw content
- **WHEN** a task payload would include raw imported material or credentials
- **THEN** the system rejects the task payload
- **AND** stores only ids, options, and safe references

### Requirement: Task Status Follows State Machine
The system SHALL transition tasks through controlled statuses. Valid statuses are `pending`, `running`, `succeeded`, `retryable_failed`, `failed`, and `cancelled`. Status changes MUST go through domain task state-machine helpers.

#### Scenario: Pending task starts
- **WHEN** a pending task is run
- **THEN** the task transitions to `running`
- **AND** a new attempt is recorded

#### Scenario: Task succeeds
- **WHEN** the invoked workflow succeeds
- **THEN** the task transitions to `succeeded`
- **AND** stores a result reference or summary

#### Scenario: Task fails retryably
- **WHEN** an attempt fails with a retryable error and attempts remain
- **THEN** the task transitions to `retryable_failed`
- **AND** records the failure in the attempt history

#### Scenario: Task fails permanently
- **WHEN** an attempt fails with a non-retryable error or max attempts are exhausted
- **THEN** the task transitions to `failed`

### Requirement: Attempts Record Execution History
The system SHALL record one `TaskAttempt` for each task execution attempt. Each attempt MUST include attempt number, status, started_at, finished_at, and error or result summary when applicable.

#### Scenario: Attempt is recorded
- **WHEN** a task runner executes a task
- **THEN** it appends an attempt record
- **AND** the attempt number increments monotonically

#### Scenario: Attempt fails
- **WHEN** a workflow call fails
- **THEN** the attempt records error code, message, stage, retryable flag, and finished_at

### Requirement: Retry Requires Retryable Failure
The system SHALL allow retry only for tasks in `retryable_failed` status. Retry MUST create a new attempt and MUST NOT edit previous attempt history.

#### Scenario: Retryable task is retried
- **WHEN** the user retries a `retryable_failed` task
- **THEN** the system creates a new attempt
- **AND** preserves previous attempts unchanged

#### Scenario: Failed task is retried
- **WHEN** the user retries a `failed` task
- **THEN** the system rejects retry
- **AND** explains that the failure is not retryable

### Requirement: Runner Calls Existing Workflows
The task runner SHALL execute business work by calling existing workflows. It MUST NOT directly mutate Source, Note, Index Entry, or Vector Index business state.

#### Scenario: Source processing task runs
- **WHEN** the runner executes a `source.process` task
- **THEN** it calls the Source processing workflow
- **AND** does not directly assign Source status

#### Scenario: Note indexing task runs
- **WHEN** the runner executes a `note.index` task
- **THEN** it calls the Note indexing workflow
- **AND** preserves approved-only indexing gates

### Requirement: Task Storage Uses Helpers
The system SHALL resolve task storage paths through storage helpers. Task files MUST be stored under `knowledge/tasks/` and MUST be validated with Zod on read and write.

#### Scenario: Task is saved
- **WHEN** a task is persisted
- **THEN** the path is generated by storage helpers under `knowledge/tasks/`
- **AND** workflow and CLI code do not hand-build `knowledge/` paths

### Requirement: Task CLI Exposes Local Operations
The system SHALL expose local task operations through CLI commands for enqueue, run, retry, show, and list.

#### Scenario: User lists tasks
- **WHEN** the user runs task list command
- **THEN** the CLI displays task ids, types, statuses, and attempt counts

#### Scenario: User runs next task
- **WHEN** the user runs task run command without a task id
- **THEN** the system runs one eligible pending or retryable task

#### Scenario: User requests JSON output
- **WHEN** the user runs task command with `--json`
- **THEN** the CLI returns machine-readable task workflow result
